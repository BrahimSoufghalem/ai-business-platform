# Pilot User Training

مدة الجلسة المقترحة: 45–60 دقيقة، ثم تمرين عملي ببيانات اصطناعية. لا يُمنح المستخدم وصولًا لبيانات حقيقية قبل إكمال التمرين.

## قبل الجلسة

- أنشئ متجر Pilot ومستخدمين منفصلين بالأدوار المطلوبة.
- فعّل MFA لدى مزود الهوية إن كان متاحًا.
- حمّل منتجات اصطناعية عبر manifest محدود.
- تحقق من Dashboard وInbox وhealth.
- جهز سيناريو طلب، نفاد مخزون، تحويل للموظف وفشل Tool.

## Owner/Manager

يجب أن يستطيع المتدرب:

- فتح لوحة Pilot واختيار 7/30/90 يومًا.
- تفسير الطلبات والمبيعات وتنبيهات المخزون وHandoff وP95/تكلفة AI.
- البحث عن correlation ID دون فتح نص رسالة في logs.
- التمييز بين Warning وCritical واختيار runbook الصحيح.
- معرفة أن لوحة القياس لا تمنح حق تعديل الرصيد أو إعادة Command Tool.
- الإبلاغ في feedback log دون هاتف أو بريد أو عنوان أو token.

## موظف المحادثات

يجب أن يستطيع المتدرب:

- فتح Inbox واستلام `pending` handoff.
- قراءة الملخص المنقح والتحقق من بيانات النظام قبل الرد.
- عدم الرد بالتوازي مع البوت أو من حساب غير المعيّن.
- تحرير المحادثة أو حلها أو إعادتها للبوت وفق الحالة.
- عدم تأكيد طلب دون موافقة صريحة ورسالة واردة محفوظة.
- التصعيد عند خصم خارج السياسة أو غموض المنتج أو فشل Command Tool.

## مسؤول التشغيل

يجب أن يستطيع المتدرب:

- فحص `/health/live` و`/health/ready`.
- قراءة structured logs باستخدام correlation ID.
- تشغيل secret/dependency/evaluation gates.
- إنشاء backup وتجربة restore على قاعدة منفصلة آمنة.
- تدوير سر وإيقاف التكامل المتأثر.
- تفعيل Safe Handoff عند ارتفاع الفشل أو latency.

## تمرين القبول

ينفذ المتدرب الخطوات التالية ببيانات اصطناعية:

1. يبدأ محادثة طلب ويحدد منتجًا وVariant.
2. ينشئ Draft ويراجع السعر والمخزون.
3. يؤكد الطلب مرة واحدة ثم يعيد الطلب نفسه ليثبت idempotency.
4. يسبب حالة تحتاج Handoff، ثم claim وrelease/resolve.
5. يعثر على trace من الرسالة إلى Tool والطلب.
6. يستجيب لتنبيه مخزون دون تعديل مباشر للرصيد.
7. يسجل ملاحظة في القالب دون PII.
