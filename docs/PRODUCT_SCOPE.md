# Product Scope — MVP v0.1

## الرؤية

تمكين التاجر الذي يبيع عبر الشبكات الاجتماعية من تشغيل متجره من نظام واحد، بحيث تتحول المحادثة إلى طلب موثوق دون أن يخمّن الـAI السعر أو المخزون أو القواعد.

## المستخدمون الأساسيون

### صاحب المتجر
- يهيئ بيانات المتجر وأنواع المنتجات والخصائص والقواعد.
- يراجع المبيعات والمخزون والطلبات وأداء الوكيل.
- يحدد حدود التفاوض ومتى ينتقل الحوار لموظف.

### الموظف
- يدير المنتجات والمخزون والطلبات حسب صلاحياته.
- يستلم المحادثات المحولة، يعدّل Draft Order عند الحاجة، ويؤكد التنفيذ.

### العميل
- يسأل عن منتج ومواصفاته وتوفره وسعره.
- يحدد Variant ويقدم معلومات الطلب.
- يحصل على رد واضح أو يتحول لموظف عند تعذر الحل الآلي.

## أهداف MVP

1. تشغيل دورة `منتج → مخزون → محادثة → Draft Order → طلب مؤكد` داخل منصة واحدة.
2. منع أي وصول بين المتاجر ومنع الكتابات غير المصرح بها.
3. جعل Product Types والخصائص والقواعد قابلة للتكوين دون تعديل الـCore.
4. إثبات أن الوكيل يجيب من بيانات موثوقة ويعرف متى يتوقف.
5. جمع قياسات Pilot تساعد على قرار بناء أول تكامل خارجي.

## ما لا يهدف إليه MVP

- بناء ERP أو Accounting كامل.
- تشغيل جميع قنوات التواصل دفعة واحدة.
- التعرف التلقائي الموثوق على المنتج من أي صورة أو فيديو.
- قرارات تسعير ذاتية أو خصومات خارج القواعد.
- Microservices أو بنية توزيع معقدة قبل وجود حمل فعلي.

## المتطلبات الوظيفية

### 1) المتجر والعزل
- إنشاء متجر وملف إعدادات افتراضي.
- ربط المستخدم بعضوية في متجر ودور: `owner`, `manager`, `agent`.
- كل قراءة أو كتابة تحدد `tenant_id` من جلسة موثوقة، لا من قيمة يرسلها العميل.
- رفض الوصول إلى أي مورد لا ينتمي للمتجر الحالي.

**معيار القبول:** اختبارات تلقائية تثبت أن المستخدم لا يستطيع قراءة أو تعديل سجل من متجر آخر حتى عند معرفة المعرّف.

### 2) المنتجات الديناميكية
- حقول أساسية ثابتة للمنتج.
- إنشاء Product Type من Template أو من الصفر.
- تعريف Attributes بأنواع مثل text, number, boolean, select وmulti-select.
- تعريف ما إذا كانت الخاصية مطلوبة، قابلة للبحث، أو تُنشئ Variant.
- التحقق من `custom_attributes` مقابل تعريف النوع عند الحفظ.
- ربط Content ID أو Product Code بمنتج محدد.

**معيار القبول:** يستطيع متجر واحد إدارة هاتف وقميص بخصائص مختلفة دون تغيير قاعدة البيانات أو الكود.

### 3) المخزون
- سجل حركات immutable قدر الإمكان: إدخال، تصحيح، حجز، تحرير، بيع وإرجاع.
- عدم تعديل الرصيد مباشرة من واجهة المستخدم.
- دعم الرصيد حسب Variant.
- منع الرصيد السالب إلا بسياسة متجر صريحة وغير مفعلة افتراضيًا.

**معيار القبول:** مجموع الحركات يطابق الرصيد المعروض، وتأكيد طلبين متزامنين لا يبيع آخر قطعة مرتين.

### 4) الطلبات
- حالات مضبوطة: `new → confirmed → preparing → shipped → delivered` مع `cancelled` من الحالات المسموحة.
- Draft Order منفصل عن الطلب المؤكد.
- كل انتقال حالة يمر عبر Use Case يتحقق من الصلاحية والقواعد.
- حفظ Snapshot للسعر واسم المنتج وVariant عند إنشاء بند الطلب.

**معيار القبول:** الانتقالات غير الصالحة تُرفض، وإلغاء الطلب يحرر الحجز مرة واحدة فقط.

### 5) العملاء والمحادثات
- ملف عميل، وسائل الاتصال، العناوين، الملاحظات والطلبات السابقة.
- Conversation وMessages مع مصدر الرسالة وهوية المرسل.
- ربط المحادثة بعميل ومنتج/طلب عند توفر السياق.
- تصنيف حالة المحادثة: `bot`, `needs_human`, `human`, `closed`.

### 6) القواعد والمعرفة
- Minimum price، Maximum discount، قابلية التفاوض وقاعدة التحويل للموظف.
- FAQ وKnowledge entries بإصدارات وحالة نشر.
- إعدادات Agent خاصة بالمتجر دون Prompt حر قادر على تجاوز سياسات النظام.

### 7) وكيل العميل
- تصنيف النية واختيار التدفق المناسب.
- استخدام Tools للبحث عن المنتج والسعر والتوفر والقواعد.
- طلب المعلومات الناقصة تدريجيًا.
- إنشاء Draft Order ثم التأكيد فقط عند تحقق البيانات والسياسة.
- التحويل للموظف عند انخفاض الثقة أو الاستثناء أو طلب العميل.

## متطلبات غير وظيفية

- **الأمان:** لا أسرار في المستودع، تشفير أثناء النقل، audit للأفعال الحساسة، وRate Limiting.
- **الاعتمادية:** العمليات المالية والمخزنية Idempotent، والـWebhooks قابلة لإعادة المحاولة.
- **الأداء المستهدف للـPilot:** API اعتيادي p95 أقل من 500ms باستثناء مزودي AI؛ بدء رد الوكيل خلال 6 ثوانٍ في الظروف الطبيعية.
- **المراقبة:** Correlation ID من الرسالة حتى Tool Call والطلب، مع تكلفة وزمن كل AI Run.
- **قابلية الاختبار:** Domain rules بلا اعتماد مباشر على Framework أو مزود AI.

## مؤشرات نجاح Pilot

هذه أهداف أولية وليست وعودًا إنتاجية:

- صفر حادث عبور بيانات بين المتاجر.
- 100% من تغييرات المخزون الحساسة لها Audit وسبب.
- ≥ 80% إجابات صحيحة على مجموعة تقييم الأسئلة المباشرة.
- 100% من حالات عدم اليقين المتعمدة تتحول لموظف بدل التخمين.
- ≥ 60% من المحادثات المؤهلة للشراء تصل إلى Draft Order صحيح.
- قياس تكلفة AI لكل محادثة وطلب مؤكد منذ اليوم الأول.
