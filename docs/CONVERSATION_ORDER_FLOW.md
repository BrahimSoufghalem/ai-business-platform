# Conversation-to-Order Flow

يحوّل وكيل العملاء رسالة الشراء إلى Draft Order ثم Order مؤكّد عبر مسار حتمي لا يستدعي نموذجًا لغويًا ولا يسمح للنموذج بحساب السعر أو تنفيذ التأكيد.

## التسلسل

1. يحدد Router طلب الشراء أو التعديل أو الإلغاء أو التأكيد.
2. يبحث الوكيل عن المنتج والـVariant، ويطلب توضيحًا إذا كانت النتيجة غير وحيدة.
3. يتحقق من الكمية المتاحة قبل أي كتابة.
4. يقرأ السعر الحالي أو يقيّم عرض العميل باستخدام إصدار قاعدة منشور.
5. ينشئ Draft أو يحدّثه مع `expectedVersion`، ويربطه بالمحادثة.
6. يجمع الهاتف والعنوان تدريجيًا. عنوان الـMVP يحتاج `line1` و`city`، ويستخدم `DZ` كرمز البلد.
7. يعيد التحقق من المخزون ثم ينقل المسودة إلى `awaiting_confirmation`.
8. يعرض ملخصًا دقيقًا يتضمن الكمية، سعر الوحدة، الخصم، الشحن والإجمالي.
9. لا يؤكد إلا من رسالة عميل واردة تطابق عبارة تأكيد صريحة مثل `أؤكد الطلب`.
10. يعيد فحص النسخة، المخزون وقرار التسعير، ثم ينشئ الطلب والحجوزات ذريًا.

```text
رسالة شراء
  → اختيار المنتج والـVariant
  → فحص المخزون والسعر/العرض
  → Draft + جمع الهاتف والعنوان
  → awaiting_confirmation + ملخص دقيق
  → رسالة تأكيد صريحة
  → Order confirmed + Stock reservations
```

## أدوات الطلب

| الأداة                         | الغرض                                                        |
| ------------------------------ | ------------------------------------------------------------ |
| `get_draft_order`              | تحميل المسودة المرتبطة بالمحادثة فقط                         |
| `evaluate_price_offer`         | قبول/مقابلة/رفض العرض وفق قاعدة منشورة وحفظ Pricing Decision |
| `create_or_update_draft_order` | إنشاء أو تعديل المسودة مع نسخة متوقعة وموقع مخزون صالح       |
| `submit_draft_order`           | إعادة فحص المخزون وإظهار الملخص النهائي                      |
| `confirm_draft_order`          | التحقق من رسالة الموافقة وإنشاء الطلب والحجوزات ذريًا        |
| `cancel_draft_order`           | إلغاء مسودة غير مؤكدة                                        |

كل أداة تعمل داخل Tenant/Conversation ثابتين يحددهما الـAPI، وتملك Input/Output schema مغلقًا. لا يستطيع نص العميل أو مخرجات النموذج تغيير هذا السياق.

## التفاوض

- `accept`: يحفظ القرار الدقيق ويستخدم `decidedPrice`.
- `counter`: يعرض السعر المقابل ولا ينشئ أو يحدّث Draft حتى يرسل العميل طلب شراء جديدًا بالسعر المقابل.
- `reject`: يرفض بأدب ولا يكتب Draft.
- `handoff`: يحوّل لموظف حسب السياسة.

يحفظ كل Item:

- `listPrice`: سعر الكتالوج قبل الخصم.
- `unitPrice`: السعر النهائي.
- `pricingDecisionId`: القرار الذي أجاز الخصم، أو `null` عندما لا يوجد خصم.

تمنع قيود قاعدة البيانات تخفيض `unitPrice` دون قرار مطابق لنفس المتجر والمنتج والـVariant والعملة والسعر وإصدار قاعدة منشور.

## التأكيد والتزامن

- كلمة عامة مثل `نعم` لا تكفي؛ يعاد عرض الملخص وتطلب العبارة الصريحة.
- يتحقق Adapter من أن `approvalMessageId` يعود لرسالة `inbound/customer` في المحادثة نفسها.
- مفتاح التأكيد هو `agent-confirm:<conversationId>:<approvalMessageId>`.
- إعادة نفس الرسالة أو إرسال تأكيد صريح آخر بعد نجاح الطلب يعيد الطلب المرتبط ولا ينشئ طلبًا أو حجزًا ثانيًا.
- كل تعديل يستخدم `expectedVersion`. النسخة القديمة تعيد نتيجة `stale` بدل الكتابة فوق تغيير أحدث.
- نفاد المخزون أثناء الإنشاء أو الإرسال أو التأكيد يعيد `out_of_stock` ولا يترك كتابة جزئية.

## التعديلات والإلغاء

- تغيير الكمية أو الهاتف أو العنوان يحدّث المسودة النشطة.
- تغيير الـVariant يعيد البحث وفحص السعر والمخزون.
- تعديل Draft كان ينتظر التأكيد يعيده إلى `draft` ثم يعاد إرساله بعد اكتمال البيانات.
- إلغاء المسودة مسموح قبل التأكيد. إلغاء Order مؤكد يتحول لموظف.
- يدعم Runtime حاليًا سطر Variant واحدًا في المسار الآلي؛ تعديل مسودة متعددة العناصر يتحول لموظف.

## الاستجابة والتتبع

استجابة `agent-reply` تضيف `draftOrderId`, `orderId` و`orderNumber` عند توفرها. جميع الأدوات والنتائج تسجل في `ai_runs` و`ai_tool_calls` بعد التنقيح، بينما تبقى بيانات العميل التفصيلية خارج النصوص التشخيصية.
